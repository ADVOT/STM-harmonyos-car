## 任务6 红外对管收发（工程 `2.0_TCRT_Timer`，源 `TCRT.c`）

- **硬件**：左 GPIO13 / 右 GPIO14，红外接收，普通 GPIO 输入；低电平（灯灭）= 黑色。接收端同时连了 STM32 PA11/PA12（留给后期改 STM32 处理）
- **核心 API**：`osTimerNew(func, osTimerPeriodic, arg, attr)` 建周期定时器 → `osTimerStart(id, ticks)` 启动（`osTimerStop/Delete` 停/删）；`GpioInit`/`IoSetFunc`/`GpioSetDir`/`GpioGetInputVal`
- **骨架**：1 线程（栈 10240、prio 25）内建 1 个周期定时器（`5U` = **50ms** 一轮，Hi3861 上 1U=10ms；文档注释"10秒"是错的），回调读 GPIO13/14 打印 `left/right black/white`
- **现象**：串口周期打印左右传感器黑白状态
- **实测（8-26 ✅ 烧录跑通）**：50ms 周期打印正常；**手遮住传感器=black、拿开=white**。⚠️ 当时的解释"无反射归 black"**8-28 已翻案**：USER近距离受控实测实为 **5cm 内有反射面=black、悬空/超 5cm=white**（手遮=black 正是"近处有反射面"），详见 `桌面防坠落-推进方案.md` §2。代码为我写的带注释版（USER基础不够先通读理解）；嫌 50ms 刷屏快可把 `osTimerStart` 改 100U=1s |
- **作业**：建 2 个软件定时器——一个 3 秒间隔打印 "hello QST"；另一个控制红外对管按不同间隔扫描，观察现象
- **API 考点**：`osTimerNew` 不能在中断里调用

## 任务7 GPIO 驱动舵机（工程 `3.0_SG90_Mutex`，源 `SG90.c`）

- **硬件**：SG90 舵机接 **GPIO2**，纯 GPIO 位拍打模拟 PWM（没用硬件 PWM 外设）
- **脉冲参数**：20ms 周期；高电平 0.5/1.0/1.5/2.0/2.5ms = 0°/45°/90°/135°/180°；`set_angle(duty)` = 高 `duty`µs + 低 `20000-duty`µs，每个角度连发 **10 次**
- **核心 API**：`osMutexNew(NULL)` → `osMutexAcquire(id, osWaitForever)` → `osMutexRelease(id)`；`hi_udelay(us)` 微秒延时
- **骨架**：互斥锁 1 个 + 线程 3 个（栈 4096）：
  - `thread1`（prio 26）：启动延时 1s，抢锁 → flag=90、舵机 90° → 持锁 5s → 释放
  - `thread2`（prio 25）：不抢锁，打印各线程运行状态和 flag 角度
  - `thread3`（prio 24）：无启动延时**先抢到锁**，flag=180、舵机 180°，持锁 3s
  - 演示点 = **优先级翻转**：低优先级 thread3 先持锁，高优先级 thread1 只能等
- **现象**：舵机先 180°、3s 后 90°，往复；串口交替打印
- **实测（8-26 ✅ 烧录跑通）**：现象与预期一致——复位后车头云台先打 180°（thread3 无延时先抢锁）、3s 后回 90°（thread1），往复循环；串口 thread1/3 交替 + thread2 穿插报角度。我版代码把 `osMutexNew` 挪到建线程**之前**（修正参考答案顺序隐患）。烧录链路：编译在 VM → **scp 把 bin 拉回 `out/wifiiot/` 再 HiBurn**（本地那份才是要烧的，别烧到旧固件）。源码已备份 `backups/harmony_app/3.0_SG90_Mutex/`
- **作业**（注意：**同优先级** 3 任务 + 互斥锁，与参考答案的不同优先级不同）：任务1 先运行、打印 1 次"任务1开始运行"、舵机左转 45°；任务3 在任务1 运行 3 秒后再运行、打印 2 次、舵机右转 45°；任务2 在任务3 后立即运行、打印 3 次、舵机居中

## 任务8 GPIO 驱动超声波（工程 `4.0_Hcsr04_Tick`，源 `Hcsr04.c`）

- **硬件**：HC-SR04，**Trig=GPIO7（输出）/ Echo=GPIO8（输入）**；量程 2-400cm
- **核心 API**：`hi_get_tick()` 读系统 tick；`hi_get_us()` 微秒时间戳（**测距实际用的是它**，教学点是 tick 而已）；`hi_udelay`；`WatchDogDisable()` 关看门狗
- **测距流程**：Trig 发 20µs 高电平（协议 ≥10µs）→ 轮询 Echo，上升沿记 `hi_get_us()`、下降沿算差 → `distance = time × 0.034 / 2`（cm）
- **骨架**：1 线程（栈 10240、prio normal），每 2s 测一次打印
- **现象**：串口周期打印 `distance is %.1f (cm)`
- **实测（8-26 晚 ✅ 烧录跑通）**：复位后 `start test hcsr04` + 每 2s 一条距离，**手在探头前移动数值实时跟随**。源码为自写带超时版（备份 `backups/harmony_app/4.0_Hcsr04_Tick/`）：等 Echo 上升/下降沿两个循环各带超时（100ms/60ms），超时返回 -1 打印 `hcsr04 timeout (no echo)`，不再死等；引脚初始化从参考答案"每次测距重配"挪到入口只配一次；`hi_get_us()` 实为 `hi_u64` 微秒时间戳（`vendor/hisi/.../include/hi_time.h`）
- **作业**：2 个软件定时器——一个 3 秒间隔测距；一个打印当前 tick 值。**✅ 已完成（8-26 晚，USER自写）**：3s 定时器回调置 Flag → 线程见标志测距；1s 定时器回调打印 `hi_get_tick()`。实测 tick 每行 +100（1s=100tick 实锤）、tick 行与距离行 3:1 频率比，符合预期。源码备份 `Hcsr04_homework.c`（同目录另有我的参考版 `Hcsr04_homework_ref.c`）
- ~~**隐患**~~：`GetDistance()` 里 `while(1)` 死等 Echo **无超时退出**，Echo 异常会卡死（靠关看门狗硬扛）——**已在本版修掉（超时保护）**，留档作教训

## 任务9 UART 信息收发（工程 `5.0_Uart_BLE`，源 `Uart.c`）

- **硬件**：**UART1**（GPIO0=TX / GPIO1=RX）接车上 JDY-16 蓝牙模块；**9600/8/1/N**（文档注释写 115200，以代码为准）
- **前置**：安卓手机装 `tools/蓝牙调试器/蓝牙调试器xnj.lazydog.btcontroller.apk`，搜 **JDY-16** 连接
- **核心 API**：`UartInit(WIFI_IOT_UART_IDX_1, &attr, NULL)`、`UartRead`/`UartWrite`；`osMessageQueueNew(16, 100, NULL)` → `osMessageQueuePut` / `osMessageQueueGet(..., osWaitForever)`
- **骨架**：消息队列 1 个 + 线程 3 个（同 prio 25）：
  - `UART_Task`：初始化串口 → 循环写 "Hello, QST!" → **阻塞**等队列消息、收到打印
  - `thread2`：`UartRead` 收蓝牙数据 → 补 `\0` → 入队 → 睡 1s
  - `thread3`：空转，每 3s 打印"任务3正在运行！"
- **现象**：手机蓝牙调试器发字符串 → 开发板串口助手显示收到；板上 UART1 循环往外发 Hello QST
- **实测（8-26 晚 ✅ 烧录跑通）**：自写版四处改进（队列传值不传指针——结构体带 `char Buf[100]`、Put 整条拷进队列节点；先补 `\0` 再打印；空读不入队；Idx 当递增序号），手机连发多条序号 `#0 #1 #2` 严格递增 = FIFO 成立。**实测发现**：手机 1s 内快速连发会被一次 `UartRead` 合并成一条——UART 是字节流无消息边界，轮询窗口内攒的字节一次读完；拆分要靠帧格式（分隔符/帧头），这正是任务24 双核协议要解决的问题。源码备份 `backups/harmony_app/5.0_Uart_BLE/`
- **作业** ✅（8-27，USER自写）：thread3 每 3s 连发 5 条消息（first~fifth，序号 #100~#104），UART_Task 阻塞取出依次打印验 FIFO；追加改造：UART_Task 启动发一次 "Hello,I'm ready!"，之后收到 `ready` 前缀（strncmp 前 5 字符，兼容全角？/APP 尾部换行）才回复——原"每轮无条件 UartWrite"会被 5 连发触发成手机刷屏。备份 `backups/harmony_app/5.0_Uart_BLE/Uart_homework.c`
- **隐性坑**：队列传的 `msg.Buf` 是指针、指向 thread2 栈缓冲，靠 sleep(1) 错开读写——演示级写法，正式用要拷内容
- **8-27 更正/新坑**：`UartRead` 是**阻塞读**（反汇编实锤调用链 UartRead→HalUartRead→hi_uart_read→uart_read→`hi_event_wait`，空缓冲 = 线程挂起等接收事件）——上文 thread2 的"每秒轮询"实为阻塞等待，当时未暴露只因另有线程在跑。读前须 `UartIsBufEmpty` 查空（SDK 已实现但 `wifiiot_uart.h` 漏声明，手动 extern）。另：蓝牙改名工具 `5.1_BLE_Rename` ✅（8-27，JDY-16 → `Gamer_0o0`）：AT 指令仅未连接态有效、必须 `\r\n` 结尾、`AT+NAME` 无参数=查询/跟参数=设置（网帖的 `AT+NAME?` 会把 `?` 当参数设成名）；固件 printf 中文字符串在 GBK 终端乱码，进固件的打印一律英文

## 任务10 第一阶段综合实验（工程 `6.0_Sum_Experiment_First`）

- **目标**：舵机左右旋转测距；前 15s 红外寻线；15s 后蓝牙通信；任务3 打印队列消息；任务1、2 交替运行
- **引脚汇总**：GPIO0/1=UART1 蓝牙（9600）、GPIO2=舵机、GPIO7/8=超声波、GPIO13/14=红外
- **联动机制**：全局 `uint8_t flag` 模式标志 + 单次定时器（15s）+ 互斥锁 + 消息队列
- **代码组织**（入口 `Sum_ExampleEntry`：关看门狗 → `Peripheral_Init()` 统一初始化 → 队列 → 互斥锁 → 4 线程，**全栈 4K、全 prio 25 同优先级**）：
  - `thread1`：抢锁 → 舵机 0° → 测距打印 → 持锁 200ms → 释放 → `sleep(5)`
  - `thread2`：同构，舵机 180° → 测距 → `sleep(5)`；两者借锁**交替**实现左右摆头测距
  - `thread3`：启动时建 `osTimerOnce`（1500 ticks=15s）→ 置 flag=2 打印 `trace start`；循环非阻塞 `osMessageQueueGet(..., 0U)` 打印队列，睡 1s
  - `TestTask`：模式分发器，`switch(flag)`：2→`trace()`（红外寻线）、3→`bluetooth()`；每轮睡 1s
  - 定时器回调（15s 到）：flag 2→3，打印 `bluetooth start`（**"前15s寻线后蓝牙"的唯一开关**）
  - `bluetooth()`：进来先 `osTimerDelete`，然后死循环 `UartRead` → 入队（thread3 读出打印）——**模式单向切换，进蓝牙就回不去**
- **现象**：复位 → 舵机左右摆+超声波打印距离 + 红外寻线打印 black/white → 15s 后切蓝牙收发
- **参考答案的坑**（自己写时绕开）：
  - `Peripheral_Init()` 笔误：GPIO2 的 `GpioSetDir` 写成了 GPIO_1（靠 `set_angle()` 每次重设方向才没炸）
  - `trace()`/`bluetooth()` 注释写 GPIO11/12，实际是 13/14
  - flag 切换依赖 thread3 先置 2，回调里 `if(flag==2)flag=3`
- **作业**：无单独作业段（只有思考题）
