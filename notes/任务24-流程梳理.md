## 2. 原理图与串口归属（已核实定论）

双核互联已经由原理图 page2/page7 和 `学习记录.md` 三处互证，后续开工无需重复确认；需要追溯时直接查看 `docx/Schematic_QST-鸿蒙小车.pdf`。

已确认连接如下：

| 信号 | 连接 | 用途 |
|---|---|---|
| Hi3861 GPIO11 / UART2_TX | STM32 PA10 / USART1_RX | Hi3861 下发到 STM32 |
| STM32 PA9 / USART1_TX | Hi3861 GPIO12 / UART2_RX | STM32 回传到 Hi3861 |
| STM32 PA2 / USART2_TX | NFC_RX | NFC 模块 |
| STM32 PA3 / USART2_RX | NFC_TX | NFC 模块 |

因此双核通道是：

```text
Hi3861 UART2  ↔  STM32 USART1
```

不要把它和 NFC 使用的 STM32 USART2 混淆。

> **8-27 已二次核实（不再"待确认"）**：原理图 page2（Hi-3861 模块页）IO11 引脚网络标签为「STM32PA10」、IO12 为「STM32PA9」；page7（STM32F103C8T6 页）PA9/PA10 旁标注「to3861」+ IO11/IO12 网络名；`学习记录.md` 8-26 第 8 条早已记录同一结论（IO11/IO12 ↔ PA10/PA9）——三处互证，TX→RX 交叉方向正确。page7/9 另证实 PA2→NFC_RX、PA3→NFC_TX。顺带发现：STM32 还引出了 UART3-TX/RX（page7/9，目前未接外设，预留）。

两端暂定串口参数：

```text
115200 baud
8 data bits
1 stop bit
no parity
no hardware flow control
```

### 2.1 原理图核对重点

不要只看芯片引脚编号，还要确认：

- TX 必须接对端 RX，RX 必须接对端 TX；✅ 已核实
- 两块芯片共地；✅（同板 3.3VD/GND）
- 信号电平为 3.3V；✅
- PA9/PA10 没有被误接到 NFC；✅（NFC 走 PA2/PA3）
- PA2/PA3 继续保留给 NFC；✅
- SW2 切换的是 CH340 调试线路，不等于改变双核内部互联。⚠️ **半对，需补充（见下）**

**SW2 实际接法（原理图 page3「USB 串口切换」，8-27 核实）**：SW2 为 6 脚双路切换——一路把 340-RX 切到 `{IO03 ↔ IO12}`，另一路把 340-TX 切到 `{IO04 ↔ IO11}`：

- 拨向 **Hi3861 端**：CH340 ↔ Hi3861 UART0 调试口（IO03/IO04）——平时看 printf 用；
- 拨向 **STM32 端**：CH340 并入 **IO11/IO12 网络**——也就是直接挂到双核链路（Hi3861 UART2 ↔ STM32 USART1）上，**三方共线**。

含义两面性：

- **风险**：SW2 在 STM32 端时，电脑串口助手发出的字节会和 Hi3861 UART2_TX 抢同一条 PA10 网络（双推挽输出对线）；正式双核联调时若不需要电脑旁观，应拨离 STM32 端。
- **利器**：拨 STM32 端时电脑能**旁观** Hi3861 发出的协议帧（抓包对帧格式），也能用串口助手**冒充 Hi3861** 发帧测 STM32——阶段 B 的 PING/错误帧/半帧/粘帧测试完全可以先用电脑做，STM32 侧联调好后再接真 Hi3861。

原理图核实记录也见 `学习记录.md:53-60`。

## 4. 协议 v1（STM32 阶段已实现）

### 4.1 帧结构

已采用带长度字段的变长帧：

```text
[帧头 SOF][命令 CMD][参数长度 LEN][参数 PAYLOAD][校验 CHECK]
```

字段定义：

| 字段 | 长度 | 值/含义 |
|---|---:|---|
| `SOF` | 1 byte | `0xAA`，用于寻找一帧的起点 |
| `CMD` | 1 byte | 命令类型 |
| `LEN` | 1 byte | 参数字节数，最大 `MAX_PAYLOAD=16` |
| `PAYLOAD` | `LEN` bytes | 命令参数，小端编码 |
| `CHECK` | 1 byte | `CMD + LEN + PAYLOAD` 的 8 位累加和低字节 |

即：

```text
CHECK = (CMD + LEN + PAYLOAD[0] + ... + PAYLOAD[LEN-1]) & 0xFF
```

这里的 `LEN` 不是业务参数，而是为了让接收端知道一帧什么时候结束。帧头、命令、参数、校验的核心结构仍然保持清晰。

第一版暂不增加固定帧尾。长度字段负责判断边界，校验负责判断完整性；接收状态机遇到错误时重新搜索 `SOF`。如果后续实测发现噪声环境下需要更强的重同步，可以再增加帧尾或升级 CRC，不要一开始同时堆叠多种机制。

### 4.2 命令分配建议

#### `0x01 SET_SPEED`：设置双轮目标速度

参数：4 bytes：

```text
int16 left_target;
int16 right_target;
```

建议使用小端、有符号、单位为：

```text
编码器脉冲数 / 100ms
```

这样协议数值可以直接对应任务23已经验证的 PID 目标，不需要在 STM32 再做单位转换。

示例：

```text
left_target  = +280
right_target = +280
```

表示两轮以任务23验证过的前进速度运行；负数表示反向；左右值不同表示差速转向；两边为0表示停车。

注意：原厂代码注释中的速度单位是 `rad/s × 100`，与任务23的“100ms脉冲数”不是同一个量。两种单位不能混用。若老师发布的任务24明确要求使用原厂速度单位，再在协议适配层转换，不要悄悄改变 PID 内部单位。

#### `0x02 STOP`：停车

参数长度为0。STM32收到后将左右目标设为0，并清除或衰减 PID 输出。

#### `0x03 PING`：链路测试

参数可以先为空。STM32收到后回传 ACK，作为不带电机动作的通信验证命令。

#### `0x81 ACK`：确认回报

由 STM32 回传。参数为：

```text
原命令 CMD + 状态码
```

状态码定义为：

```text
0 = OK
1 = BAD_LENGTH
2 = BAD_CHECKSUM
3 = INVALID_PARAM
4 = UNKNOWN_CMD
```

坏校验、非法长度和未知命令也进入单槽事件邮箱，由主循环发送对应 ACK；它们不会更新运动目标。

#### `0x82 STATUS`：状态回报（第二阶段再做）

可用于回传左右实际速度、目标速度、当前模式、通信超时状态等。第一版先不让状态回报干扰基础运动控制。

### 4.3 协议示例

以 `SET_SPEED(+280, +280)` 为例，280 的小端表示为 `0x18 0x01`：

```text
AA 01 04 18 01 18 01 37
```

其中：

```text
SOF     = AA
CMD     = 01
LEN     = 04
PAYLOAD = 18 01 18 01
CHECK   = 01 + 04 + 18 + 01 + 18 + 01 = 0x37
```

已用 `Protocol_EncodeFrame()` 和宿主测试核对；STM32 与 Hi3861 发送端必须复用同一计算规则。

### 4.4 必须提前定下的协议规则

在写两端代码前，把以下规则写成头文件注释并保持一致：

- 字节序：统一小端；
- 速度是否有符号：统一 `int16`；
- 最大速度：STM32 侧再次限幅，不能信任 Hi3861；
- 最大 `LEN`：例如限制为16，防止错误字节导致无限等待；
- 校验范围：明确不包含 `SOF`，包含 `CMD/LEN/PAYLOAD`；
- 非法帧处理：丢弃当前帧并重新寻找帧头；
- 新帧到达时如何覆盖旧命令：运动控制只保留最新有效目标即可；
- 没有通信时的安全行为：默认停止；
- 正常运动帧是否需要周期重发：建议需要，作为心跳；
- 复位后是否允许自动运动：不允许。


初始目标为0；只有合法 `SET_SPEED` 才建立300ms运动租约。

第一版继续沿用100ms控制节拍，但控制函数每一拍从“当前外部目标”取目标速度；PID 只在主循环执行。SysTick 仅维护1ms计数、协议半帧超时和 `control_due` 标志。

### 第二步：把接收中断改成二进制帧状态机

协议模块已落地于 `motor_pwm/QST_HARDWARE/protocol/protocol.c/.h`：接收 ISR 逐字节投递，解析器使用单槽事件邮箱；主循环取出事件、发送二进制 ACK，控制节拍执行 PID。`SET_SPEED` 严格 LEN=4，按小端 int16 解码并二次限制 `abs(value)<=420`；合法运动帧刷新300ms租约但不重置 PID，PING 不续租，STOP/租约超时立即清目标、PID 与 PWM。

接收路径：

```text
USART1 RXNE 中断
    ↓
读取一个字节
    ↓
protocol_parse_byte(byte)
    ↓
收到合法完整帧后写入命令邮箱
    ↓
置位 frame_ready
```

状态机至少应能处理：

1. 空闲状态等待 `SOF`；
2. 收到帧头后读取 `CMD`；
3. 读取 `LEN`；
4. 按 `LEN` 收齐参数；
5. 读取校验字节；
6. 校验通过才提交命令；
7. 校验失败时丢弃当前帧并重新同步；
8. 半帧后长时间没有新字节时复位状态；
9. 新帧的帧头出现在错误数据中时允许重新同步。

中断里只做逐字节收帧和轻量校验，不在中断里调用 PID、打印长字符串或执行电机控制。

### 第三步：安全地把完整命令交给控制层

完整帧交给主循环或控制节拍处理。不要让 USART 中断直接和 PID 变量发生复杂的多字节并发读写。

简单实现可以使用：

- 一个 `volatile` 完整帧邮箱；
- 一个 `frame_ready` 标志；
- 控制侧在安全时刻复制命令；
- 复制完成后清标志。

如果后续需要同时保留多个命令，再升级为环形队列。运动控制通常只需要最新的有效速度目标，不需要积压过期的速度帧。

### 第四步：加入命令合法性检查

STM32 必须二次检查：

- `CMD` 是否支持；
- `LEN` 是否与命令匹配；
- 速度值是否在允许范围；
- 参数是否出现不合理组合；
- 校验是否正确。

例如 `SET_SPEED` 即使收到 `+30000`，也只能按 STM32 侧设定的最大目标速度处理，不能直接交给 PID。

### 第五步：已加入通信超时停车

STM32 记录最近一次合法 `SET_SPEED` 的毫秒时间。超过300ms租约后，主循环清零左右目标、PID 状态和 PWM；重复合法 `SET_SPEED` 只刷新租约，不重置 PID。`STOP` 立即停车，`PING` 只回 ACK、不续运动租约。

## 6. USART1 调试输出冲突

任务24固件已将 USART1 定义为二进制双核协议通道：`usart.c` 保留 PA9/PA10、115200 8N1，RXNE ISR 只把收到的单字节交给 protocol；主循环通过统一帧编码发送 ACK。活动 `motor_pwm/` 工程已移除 `printf`/`fputc` 重定向，不会再用 ASCII 日志污染协议字节流。

SW2 拨到 STM32 端时，CH340 仍与双核链路三方共线（接法与风险/调试利器详见 §2.1），因此串口助手应按 HEX 观察或发送协议帧，不要发送任务19 ASCII 灯效命令。


三个接口共用 `protocol_checksum()`、`protocol_encode_frame()` 和 `protocol_send_frame()`：统一填充帧头、命令、长度，按 little-endian 编码有符号 int16 左右速度，一次 `UartWrite()` 发出完整帧。`SET_SPEED(+280,+280)` 已静态核算为 `AA 01 04 18 01 18 01 37`。

`TASK24_ENABLE_MOTION_TEST` 改为1时才执行固定低速序列：`+140,+140 → STOP → -140,-140 → STOP`；运动阶段每100ms重发速度帧，小于 STM32 的300ms租约。当前固件宏保持0。

### 第三步：上行 ACK 独立接收（已完成，待硬件验证）

ACK 接收放在独立线程中，并沿用 SDK 漏声明时的已知 `extern UartIsBufEmpty(...)` 原型。线程每次先查 UART2 缓冲区，只有非空时才调用阻塞式 `UartRead`，因此不会堵住控制线程。

读到的数据逐字节送入 `SOF/CMD/LEN/PAYLOAD/CHECK` 状态机，不假设一次读取等于一帧；解析器限制 `MAX_PAYLOAD=16` 并校验累加和。合法 `ACK(0x81,LEN=2)` 以英文打印原命令与 `OK/BAD_LENGTH/BAD_CHECKSUM/INVALID_PARAM/UNKNOWN_CMD` 状态，接收只作测试打印，不改变控制行为。

## 9. 红外传感器：原理已实测，桌面场景标定待做

> 8-27 校准：本节原标题“现有结论只是暂定”**措辞过重**。反射原理任务6 已实测定论（手遮=black/拿开=white = 反射有无的直接验证，"测的是红外反射强度"非颜色识别），任务10 架空实测全程 black 也符合“悬空=无反射”预期。真正没做过的是**桌面场景**的标定——"台面=white"至今未实测（任务10 跑车时处于架空/手持状态）。故正确定位：原理可信，桌面标定照本节清单执行。
>
> **8-28 再校准（翻案）**：USER做了近距离受控实测，极性与上文假设**相反**——**5cm 内有反射面（桌面）=black、悬空/超 5cm=white**；探测距离 ~5cm、传感器距轮纵向仅 2cm。桌面标定已完成初测，结论与防坠落设计约束见 `桌面防坠落-推进方案.md` §2（真值表已翻转）。任务10"悬空全程 black"与本次矛盾，疑为手持时传感器下方有身体/桌面入窗，以受控测量为准。

### 9.1 目前知道什么

任务6使用的是左右两个红外对管：

- Hi3861 GPIO13：左；
- Hi3861 GPIO14：右；
- 任务6当时按50ms周期采样；
- 已观察到手遮住时显示 `black`，拿开时显示 `white`。

当前的解释是：传感器输出更接近“红外反射强度经过模块比较器后的数字结果”，不一定是真正的颜色识别。

因此“black”可能意味着：

- 没有检测到足够反射；
- 传感器悬空，距离桌面太远；
- 表面颜色深、吸收红外；
- 传感器被手或其他物体遮挡；
- 供电、安装角度、环境光导致输出变化。

这也是为什么目前不能把“读到 black = 一定掉到桌外”当成已验证事实——**原理上 black=无反射≈悬空成立，但桌面场景（台面反射率、临界距离、安装高度）的实测标定还没做**。

### 9.2 必做的重新标定项目

在真正写防坠落真值表之前，分别测试左、右传感器：

| 场景 | 需要记录 |
|---|---|
| 正常桌面中心 | GPIO原始值和稳定性 |
| 靠近桌沿但仍在桌面 | 距桌沿距离、是否提前变化 |
| 传感器悬空 | 输出值、从离地到变化的高度 |
| 浅色桌面 | 是否稳定识别 |
| 黑色/深色桌面 | 是否误报悬空 |
| 白纸、黑纸、木板、金属等表面 | 反射差异 |
| 不同安装高度和角度 | 检测窗口变化 |
| 手遮挡、灰尘、强环境光 | 误触发情况 |
| USB供电与电池供电 | 电源变化是否影响输出 |

每种场景不要只看一次打印，至少连续观察一段时间，记录：

- GPIO 读值；
- 当前软件显示的 black/white；
- 左右传感器是否一致；
- 从正常地面到悬空时的响应延迟；
- 回到地面后是否立即恢复；
- 临界位置是否抖动。

### 9.3 软件上不要把 black/white 写死成业务语义

建议先使用中间抽象：

```text
sensor_raw_left
sensor_raw_right
floor_detected_left
floor_detected_right
```

在标定阶段明确：

```text
floor_detected = 原始值满足“检测到可行驶地面”
```

如果实测发现当前模块的有效电平与现有笔记相反，只需修改传感器转换层，不要修改协议命令和 STM32 执行代码。

### 9.4 去抖参数（8-28 晚已落地为"非对称去抖"，实机后仍需校准）

受传感器距轮 2cm、140 档制动窗口 ~100ms 约束，原先"连续3次一致（150ms）"起步方案太慢，已废弃。阶段F 实现采用**非对称去抖**：

- 采样周期 50ms，控制周期 10ms；
- **危险方向（出现探空）N=1 拍**：单个 white 立即触发边缘状态，最快 ~50ms 内停车；
- **安全方向（恢复有地面）N=2 拍（100ms）**：防止污渍/抖动把探空误判成安全；
- 传感器快照超过 120ms 未更新视为数据过期，立即 STOP 并要求重新去抖；
- 恢复动作有最短持续时间（后退 ≥500ms、转向 ≥600ms），避免每拍反复切换。

这些仍是起始实验参数：实测误报过多就加大安全去抖或降速，刹不住就缩短采样周期或降速档。

## 10. 防坠落决策状态机（8-28 已实现，实机待验）

### 10.1 建议状态

```text
NORMAL       正常行驶
EDGE_LEFT    左侧异常
EDGE_RIGHT   右侧异常
EDGE_BOTH    两侧异常
RECOVER      后退/转向恢复
```

8-28 晚在 `F.0_Tabletop_Cliff_Avoidance` 中按以上骨架实现，并额外增加了 `FAULT_STOP`（恢复重试 3 轮失败后锁存停车，需重启清除）。动作时间参数：边沿先 STOP 100ms → 后退（单边 500~1000ms、双边 700~1200ms）→ STOP 100ms → 原地转向（单边 600ms、双边 800ms）→ 静置 100ms 后判下一站。EDGE_BOTH 中若仅一侧先恢复，按"仍探空的一侧"选择避让方向（左探空→右转、右探空→左转），双边都安全才固定转向（当前宏 `BOTH_EDGE_TURNS_RIGHT=1`）。

### 10.2 初始决策表

下表已按 8-28 实测极性在阶段F 代码中实现（动作 = 先 STOP → 后退 → 原地转向恢复）；实机验证前仍按候选参数处理：

| 左侧地面检测 | 右侧地面检测 | 候选解释 | 候选动作 |
|---|---|---|---|
| true | true | 两侧都有可行驶地面 | 正常前进 |
| false | true | 左侧可能探空 | 后退并向右避让 |
| true | false | 右侧可能探空 | 后退并向左避让 |
| false | false | 可能正对桌沿，或两传感器同时受干扰 | 先后退，再原地转向 |

若实测得到的传感器语义不同，只修改“原始值 → true/false”的转换和这张表。

### 10.3 状态机纪律

- 正常状态下持续发送速度心跳；
- 进入边缘状态后，不要每50ms无条件切换左右转；
- 后退和转向动作要有最短持续时间，避免只动一拍；
- 恢复到安全地面后再回到正常行驶；
- 双传感器异常时默认采取更保守动作；
- 任何通信异常最终都由 STM32 超时停车兜底；
- 桌面实测必须从低速、短时动作开始。

## 11. 当前已知风险

### 11.1 串口复用风险（软件冲突已消除，物理共线仍需注意）

任务24 STM32 固件已移除 USART1 的 `printf`/`fputc` 和任务19 ASCII 解析，USART1 只承载二进制协议，软件层污染已消除。剩余风险来自 SW2 拨 STM32 端时 CH340、Hi3861 UART2、STM32 USART1 三方共线：电脑和 Hi3861 不能同时向 PA10 发送，电脑冒充测试期间不要运行会初始化 UART2 TX 的 Hi3861 固件。

### 11.2 上电自动运动风险（已通过代码消除，待实车验证）

任务23旧代码的自动一米行程已留底到 `backups/motor_pwm_main_task23_final.c`，活动任务24固件上电目标/PWM均为0；只有合法 `SET_SPEED` 才启用300ms运动租约，STOP或超时立即清目标、PID和PWM。仍需通过架空实测确认复位默认停车和断流停车。

### 11.3 单位风险

原厂 `robot_l9110s.c` 的速度注释和任务23 PID 的编码器脉冲单位不同。协议必须只有一个明确单位，推荐第一版直接使用“脉冲/100ms”。

### 11.4 左右轮和方向风险

Hi3861 原厂函数使用左、右顺序；STM32 `Set_Pwm(left, right)` 也使用左、右顺序，但底层 TIM 通道映射存在电机 A/B 与物理左右的转换。必须架空逐轮验证，不能只凭变量名判断。

### 11.5 传感器语义风险

黑白显示值不等于“安全/危险”结论。桌面颜色、红外反射率、传感器高度和遮挡都可能改变结果。防坠落真值表在传感器实验完成前只能作为候选方案。

### 11.6 Hi3861 阻塞读风险（已隔离，待实链路验证）

ACK 接收已放在独立线程，并先用 `UartIsBufEmpty` 查缓冲区，只有非空时才调用 `UartRead`，不会堵住控制线程。后续加入红外决策时继续保持这层隔离；真实 ACK 连续到达、半帧和粘帧仍需硬件联调验证。
